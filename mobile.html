01 / FIELD NOTES

Separate the app, platform and backend

Changing a client check is not necessarily a server-side authorization failure.

Inventory app permissions, local files, caches, logs, backups, key-store use, IPC/deep links, WebViews and network requests. Model an attacker with a normal app, physical access, a modified client or a compromised device separately. Use MASVS to select required properties and MASTG to design checks; preserve the versions and test identifiers used.

02 / FIELD NOTES

Follow sensitive data and exposed interfaces

The question is who can read or invoke something in the stated model.

Test questionMethod / evidenceInterpretation
Storage / key managementInspect synthetic secrets in files, logs, backups and platform key APIsDevice encryption and per-app access controls have different assumptions
IPC / deep links / WebViewInvoke an exposed component with a test app or controlled linkCaller validation and backend permission must both hold
Network trustReview certificate validation and observe traffic using a lab certificate configurationInstrumentation setup must be separated from a deployment trust flaw
Client-enforced privilegeRepeat the corresponding backend request with a lower-privilege test identityA UI restriction cannot replace server-side authorization

03 / FIELD NOTES

Combine static and dynamic observations

Package inspection proposes questions; runtime behavior tests them.

Read the package manifest and relevant code paths, then correlate them with runtime calls, storage and traffic. Frida can expose arguments and returns in a controlled build; its ability to modify execution reflects the instrumentation privileges you granted. Record emulator versus real-device behavior, build type and OS version. Anti-tamper controls may raise attacker cost but do not replace backend security.
