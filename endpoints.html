01 / FIELD NOTES

Begin with the process and its authority

A process can act through files, services, credentials, IPC and the kernel.

On Linux, examine users/groups, sudo policy, file permissions, capabilities, scheduled jobs, service configuration and namespace boundaries. On Windows, examine access tokens, service/object ACLs, scheduled tasks, elevation boundaries and application configuration. Separate “a low-privilege user can edit this input” from “a privileged process later consumes it in a dangerous way”; both need evidence.

02 / FIELD NOTES

Understand the bug before assigning exploitability

A crash, a memory corruption primitive and a reliable security impact are distinct milestones.

AreaQuestionUseful evidence
Parsing and memory safetyCan untrusted input violate bounds, lifetime or type assumptions?Minimized reproducer, stack trace and sanitizer result
Logic / authorizationCan valid operations cross a privilege boundary?Principal, object and privileged effect
MitigationsWhich memory and process protections apply here?Actual build flags and runtime state

Ghidra provides static analysis; a debugger and Frida provide runtime observations. Decompiled output is an interpretation, not guaranteed source code. Confirm types, control flow, symbol assumptions and observed behavior. A local finding is not automatically a remote attack path.

03 / FIELD NOTES

Fuzz a boundary with a useful harness

The harness decides what code and states the experiment can reach.

Pick an input boundary, create a small valid seed corpus, instrument coverage and add relevant sanitizers. Make the harness deterministic enough to reproduce failures and reset state between inputs. Deduplicate crashes by root cause, minimize a testcase and determine security relevance. More executions per second do not compensate for a harness that never reaches the sensitive parser.

Read the source: AFL++ documentation ↗

04 / FIELD NOTES

Review the delivery and recovery boundary

Host security also depends on update trust, local secrets and operational state.

Check which identity can install or replace an executable, who controls its configuration, how updates are verified and what survives a rollback. For an authorized impact check, a harmless marker or a controlled read of a synthetic fixture can establish a boundary crossing without collecting unrelated host data. Record the exact cleanup state and verify the service still behaves normally after restoration.
