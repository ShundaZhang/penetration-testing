AI system security / FIELD GUIDE

Test the AI system
not only its prompt

LLM applications, retrieval, agent tools, model artifacts and adversarial machine learning.

01 / FIELD NOTES

Draw the system before generating probes

Model, orchestrator, retrieval store, connectors and tool credentials have different authority.

List trusted instructions, untrusted inputs, retrieved documents, long-term memory, available tools and protected resources. Include the conventional web/API and IAM layers: an AI service can have ordinary authorization flaws as well as AI-specific failures. State attacker knowledge and access separately for direct prompts, retrieved content, training data and model artifacts.

02 / FIELD NOTES

Injection becomes a security finding at a boundary

A surprising answer is not the same as unauthorized resource access.

Test questionMethod / evidenceInterpretation
Direct / indirect prompt injectionPlace controlled instructions in a user prompt or a synthetic retrieved documentRecord whether the app reveals a protected fixture or performs a forbidden action
Retrieval isolationCreate two tenant corpora and compare retrieved document identitiesSimilarity search must not replace access filtering
Memory contaminationUse resettable sessions and track which content becomes durable memorySeparate current-context behavior from cross-session persistence
Output handlingInspect where generated text becomes HTML, a query, code or a tool argumentTreat model output as untrusted input to downstream interpreters

03 / FIELD NOTES

Test delegated tools as a confused-deputy problem

The model should not be able to spend authority the user or workflow did not grant.

For MCP and other connector interfaces, inspect tool schemas, provenance, authentication, scopes, audience and per-user resource checks. Test whether a low-privilege user can induce a high-privilege connector to access a synthetic protected record. Verify outbound destination controls and action-specific authorization in the tool service, not only in the system prompt. Connector discovery, tool invocation and resource authorization are distinct stages.

04 / FIELD NOTES

Model-level attacks need a stated threat model

Capabilities over training data, inference inputs and artifacts lead to different experiments.

DirectionQuestionInterpretation
Evasion / adversarial examplesCan bounded input changes alter a meaningful decision?Measure allowed perturbation, task impact and baseline
Data / model poisoningCan permitted data or artifact influence create targeted failures?Document attacker control and persistence across retraining
Privacy / extractionCan queries reveal protected examples or approximate guarded functionality?Use synthetic canaries and account for chance and public knowledge
Supply chainCan an untrusted artifact or dependency execute or alter trusted behavior?Track artifact format, loader behavior and signature/provenance

05 / FIELD NOTES

Use evaluators as measurements with limits

Test app effects in addition to model responses.

garak provides LLM probing, and PyRIT provides configurable AI risk-evaluation workflows. Pin the model, app build, retrieval corpus, tool policy and evaluator configuration. Use deterministic checks for actual reads/writes and human review for ambiguous cases. Repeat stochastic cases with a reported trial count; distinguish a jailbreak, a policy violation and a confirmed unauthorized action. A classifier’s hit is not automatically a validated exploit.
