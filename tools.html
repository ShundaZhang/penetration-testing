01 / FIELD NOTES

A tool is an instrument with a contract

Understand its inputs, traffic, side effects and result semantics.

Start with a question and the least complex instrument that can answer it. Record tool version, target scope, identity, configuration, plugins/templates and timestamp. Distinguish a passive parser from an active scanner, a credentialed audit from an exploit check, and a configuration recommendation from a demonstrated failure. Kali and similar distributions package tools; the distribution is not a methodology.

03 / FIELD NOTES

Three results that need careful interpretation

Tool output is a starting point for reasoning.

ResultWhat it supportsNext check
Version/CVE matchA potentially relevant known issueVendor backports, build, exposure and required configuration
Template hitA template’s conditions matched a responseInspect request, matcher, false positives and claimed impact
Permission path / policy alertA relationship or policy deserves reviewValidate effective permission, state and final resource access

Nuclei templates and scanner plugins can contain executable or intrusive behavior. Review the selected checks, pin the ruleset and keep the request budget visible. Metasploit modules vary in prerequisites and effects; an available module is not proof that a target is vulnerable.

04 / FIELD NOTES

Start with a small, observable setup

A browser, proxy, terminal and evidence notebook are enough for the first application exercise.

# Inspect only the local learning server you started
curl --include http://127.0.0.1:8768/
# Save the paired request/response and explain the tested property

Add automation after you can explain one request manually. Prefer official project releases; keep disposable labs separate from unrelated services, and capture changes required for rollback. Do not copy an entire tool suite into a workflow just because it is available.
