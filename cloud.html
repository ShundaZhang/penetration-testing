01 / FIELD NOTES

Evaluate the effective permission chain

Cloud reachability and cloud control are not the same thing.

Trace principal → credential/session → applicable policies → action → resource. AWS decisions can involve identity policies, resource policies, boundaries, session policies and organization controls; evaluate their exact interaction rather than assuming all permissions are simply added. Check role trust, who can assume or pass a role, and whether a workload can obtain an identity stronger than intended. Treat cloud and provider testing policies as part of the agreed scope.

03 / FIELD NOTES

Kubernetes has several interacting boundaries

RBAC, workload isolation, network policy and the node boundary each answer a different question.

Inventory API access, service accounts, RoleBindings/ClusterRoleBindings, admission policy, secrets, container capabilities, host mounts and network policy enforcement. A namespace is an organizing and policy scope; it does not alone guarantee tenant isolation. Privileged containers or host access may weaken the pod/node boundary. A kube-bench configuration result and an image CVE report are not proof of a successful runtime escape.

04 / FIELD NOTES

Build a small account and cluster lab

Start with read-only inventory and test narrowly scoped permissions using disposable fixtures.

Create two identities and two storage objects with deliberately different permissions. Compare the intended policy with observed access, then fix and repeat. For Kubernetes, document a service account’s permissions and one expected-denied operation in a local cluster. Prowler and ScoutSuite help organize posture observations; keep their collected account data and API permissions visible in your test record.
